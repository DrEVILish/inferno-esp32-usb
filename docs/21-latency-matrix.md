# 21 — Round-trip latency test matrix

Targets: **10, 6, 4 and 2 ms round trip**, each at **32×32, 16×16, 8×8, 4×4
and 2×2 channels**. That is 20 permutations, and every one is tested.

Generated by `tools/latency_matrix.py`; that script is the source of truth
for the profiles. Edit it, then regenerate this table with
`python3 tools/latency_matrix.py`.

## What "round trip" means here

```
Inferno TX ─net─► DUT RX ─USB IN─► host loop (JACK) ─USB OUT─► DUT TX ─net─► Inferno RX
   │                                                                              │
   └──────────── impulse at media time T ─────────── measured arrival T + RT ─────┘
```

RT is measured network-to-network, in samples, on a Linux test PC that runs
Inferno, so there are no converters in the path. Every permutation is
measured in three modes:

| mode | firmware build | path | gives |
|---|---|---|---|
| **A: system** | `LAT<t>_CH<n>` | full path above, host loops USB IN→OUT in JACK at the profile's period | the headline RT, compared with the target |
| **B: device only** | `LAT<t>_CH<n>_NETLOOP` | Inferno → DUT RX → DUT TX → Inferno (no USB) | the device + network share |
| **C: host only** | `LAT<t>_CH<n>_USBLOOP` | host plays → DUT loops USB OUT→IN → host records | host stack + USB share (calibrates `HOST_DRV_FRAMES`) |

Step 0 (calibration): Inferno TX → Inferno RX directly, with the DUT out of
the path. This measures Inferno's own buffering, which is subtracted from A
and B.

| target | AoIP latency (each way) | fpp | USB OUT lead | host period (JACK `-p`, `-n 2`) |

| 10 ms | 1 ms | 16 | 1 ms | 64 |

| 4 ms | 0.5 ms | 8 | 0.25 ms | 16 |

The 0.25 ms and 0.5 ms AoIP latencies need a direct link or one QoS switch
between the test PC and the DUT, with nothing else on the segment.

What the predictions say before any hardware:
- **10 ms and 6 ms** fit at every channel count, with margin.
- **4 ms** fits on paper (3.4 ms) but has less than 15 % margin. 32×32
  also doubles the packet rate (24k TX, up to 48k RX).
- **2 ms** with a computer in the loop is predicted to miss (2.4 ms). The
  device's share is about 0.95 ms, but the host's audio stack alone is
  estimated at 1.5 ms even at 8-frame periods. Mode B (device only) is
  predicted to pass at 0.5 ms, and mode C tells us whether a tuned Linux
  host can close the gap.
- 32×32 at 2 ms (48k packets/s) is predicted to exceed the P4's packet
  ceiling. The ceiling is an estimate until test B4 measures it.

Model correction (2026-10-13, docs/14-latency.md §2): the first version
added fpp to the device's TX share and fpp + 6 to mode B. A TX packet's
timestamp is the media time of its first sample and the receiver plays it
at timestamp + latency, so packetisation happens *inside* the AoIP latency
and is not added; `usb_in` is now the IN read margin (3) plus one microframe
of USB transit (6). Profiles (net_lat, fpp, usb_lead) are unchanged.

## Firmware support (implemented 2026-10-13)

- `UI_CHANNELS` and `UI_LAT_PROFILE` are Kconfig choices ("usb-inferno build
  profile"); `app_config.h` derives everything else. Production default:
  32 ch, profile 10.
- `tools/build-matrix.sh [NAME...]` builds `LAT<p>_CH<n>[_NETLOOP|_USBLOOP]`
  into `firmware/build-matrix/<NAME>/` (`--list` prints all 60).
- Telemetry identifies the image (`fw_build`, `fw_elf_sha256`, `cfg_*`) and
  reports the latency windows (`lat_*`, docs/14-latency.md §5) and
  `cpu0_idle_pct` / `cpu1_idle_pct` for item 5 below.

## Pass criteria (per permutation and mode)

1. **Latency.** The measured RT (median of 100 impulses) is at most the
   target for mode A. Report modes B and C alongside.
2. **Stability.** The run lasts 10 min, or 1 h for 32×32 at 6 ms and at
   4 ms. These telemetry counters must not grow:
   - `usb_*_underruns`, `usb_out_gap_fills`, `usb_in_resyncs`
   - `aoip_rx_late`, `aoip_tx_underruns`
   - `ring_*`, `ptp_epoch`
3. **Integrity.** A per-channel deterministic 24-bit pattern runs alongside
   the impulse, and every channel must stay bit-exact in modes A and C.
4. **Jitter.** The RT spread (max − min over the run) is at most 1 sample.
   The device must be sample-locked, so any spread is a bug.
5. **Record** per run: firmware build ID, telemetry snapshot at start and
   end, pps, link load, CPU idle per core, and the host period/driver.

## Order of execution

1. Mode C at the three host periods (64/16/8) × 5 channel counts. This
   finds the host floor first, because it decides whether 2 ms is possible
   at all.
2. Mode B for all 20 permutations. These are cheap and need no host
   tuning.
3. Mode A for all 20, ordered from 10 ms down to 2 ms and from 2×2 up to
   32×32, so the first failure marks the boundary.
4. Record the results in `docs/22-latency-results.md` as the same 20-row
   table with measured A/B/C and pass/fail.

## Firmware and tools needed (tracked in 30-roadmap)

- Build-time channel count (`UI_CHANNELS` = 2/4/8/16/32) across USB
  descriptors, AoIP channel lists and ring sizes.
- Build-time latency profile (`UI_LAT_PROFILE` = 10/6/4/2): AoIP latency,
  fpp, USB lead.
- `tools/build-matrix.sh` builds all 20 × {A, B (NETLOOP), C (USBLOOP)} =
  60 images into `firmware/build-matrix/<name>/`, serialized at 2 cores.
- `tools/rt_measure.py` (test PC): drives the Inferno ALSA device and JACK,
  emits impulses and patterns, computes RT/jitter/bit-exactness, and pulls
  DUT telemetry before and after the run.
- `tools/rt_matrix_run.py`: steps through the permutations, flashing each
  image, and writes the results table.
